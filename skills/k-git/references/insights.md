## Insights

- Initial baseline created automatically from insights governance standard.
- If `SSH_AUTH_SOCK` points to `$HOME/.bitwarden-ssh-agent.sock` and `ssh-add -l` returns `Error connecting to agent: Connection refused`, the socket path existing is **not** enough: Bitwarden Desktop / its SSH agent is not actually serving yet, so `git push` will still fail with `Permission denied (publickey)`.
- If Bitwarden Desktop is relaunched and `ssh-add -l` / `ssh -T git@github.com` still hang or time out, treat it as an **unlock / approval pending** state rather than a Git problem: do not force HTTPS, and ask KπX to unlock/approve Bitwarden before retrying `pull` or `push`.
- `fatal: .git/index: index file open failed: Not a directory`, seen ~1-4 times right as a hook starts (once per submodule): this is `git-hook-passthrough.sh`'s submodule loop (`submodule_dirty_report`/`submodule_push_report`) running `git -C <submodule> ...` while still carrying the hook's inherited `GIT_DIR`/`GIT_WORK_TREE`/etc — a submodule's `.git` is a file, not a dir, so a leaked git-dir path colliding with it hits ENOTDIR. Non-fatal to the actual commit/push (git recovers), but noisy. Fixed 2026-08-26 (v2.10.1) with `unset $(git rev-parse --local-env-vars)` at the top of both functions — the pattern `git help githooks` itself documents for running git against a foreign repo from a hook. Could not force-reproduce it in isolated manual testing even with a faithful relative-`GIT_DIR` simulation — the fix is applied on the strength of the documented mechanism matching the symptom exactly (same error text, same "count = submodule count" pattern as a matching real-world case: github.com/sds/overcommit#383), not on a local repro. If it recurs after this fix, that would mean the mechanism is something else and needs re-investigating from scratch, not a "the fix didn't stick" retry.
- No `ssh-agent` runs by default on `deep-pc6` (`XDG_SESSION_TYPE=tty`, no GNOME session → the documented `gcr-ssh-agent` "PREFERRED" strategy in `k-ssh/SKILL.md` never actually starts — it's undocumented-as-unwired, not broken). Every git-over-ssh op decrypts the key fresh; the submodule push gate loops per-submodule, so a passphrase-protected key gets prompted once per submodule in the same `git push` (e.g. 4 submodules = 4 prompts back to back) — looks like a bug, is actually just "no caching, N sequential connections". `ssh-add --help` alone failing with "Could not open a connection to your authentication agent" is the fast way to confirm this is the cause before chasing anything else.
- CORRECTION (2026-08-26, partially supersedes the entry above): deep-pc6 NOW has `SSH_AUTH_SOCK=$XDG_RUNTIME_DIR/gnupg/S.gpg-agent.ssh` (gpg-agent serving SSH) — but it starts each session with **no identities** (`ssh-add -l` → rc=1), so the N-prompts behavior persists until one `ssh-add` per boot/session (see k-ssh insights for the updatestartuptty ritual).
- PRE-PUSH GATE FALSE POSITIVES (fixed v2.11.0, commit 2da5e5f): `submodule_push_report()` fed `git ls-remote` stdout+stderr into one string then `cut -f1`, so ANY multi-line server banner (GitLab `remote: INFO: Your SSH key expires soon`) polluted `remote_sha` → 🔴 "HEAD not on remote/main" for submodules that WERE pushed (3/4 blocked on deep-pc6 while their SHAs matched exactly), and connection drops were misreported as mismatches instead of unreachable. Fix: extract only real ref lines via awk `length($1)==40 && $1 !~ /[^0-9a-f]/` + distinct UNREACHABLE / NOT-found / mismatch branches.
- ⚠️ Portability trap hit while fixing the gate: deep-pc6's awk is mawk WITHOUT ERE interval support — `$1 ~ /^[0-9a-f]{40}$/` silently matches NOTHING (verified live: prints "NO INTERVALS"). Never use `{n}` quantifiers in portable sh/awk; use `length()==N` + negated character class.
- Fast push-failure diagnosis trio (all non-secret): `echo $SSH_AUTH_SOCK` (socket set?) → `ssh-add -l` (identities loaded?) → `ssh -o BatchMode=yes -T git@gitlab.com` (fails fast instead of hanging; distinguishes "no identity" from real network errors like `Connection closed by 172.65.251.78`). On deep-pc6 github auth succeeds under BatchMode with zero identities → `id_ed25519_github` has NO passphrase there; only `id_ed25519_gitlab` needs the tmux ops-pane passphrase handoff.
- GitLab key metadata is queryable without secrets exposure via `glab api /user/keys` (glab keeps its token internal — zero-touch compliant). Found 2026-08-26: key `Deep-PC6` created same-day with expires_at 2026-08-29 (3-day TTL).
- `error: update_ref failed for ref 'refs/remotes/<remote>/<branch>': cannot lock ref ... Permission denied` on `git push`/`make push`, even though the log line right above it shows `[new branch] <branch> -> <branch>` (the push itself succeeded remotely): the LOCAL tracking-ref bookkeeping is blocked because `.git/refs/remotes/<remote>/` (and/or `.git/logs/refs/remotes/<remote>/<branch>`) is **root-owned** on a repo that should be entirely `kpihx`-owned — root ownership on stray files inside an otherwise-`kpihx`-owned `.git/` has recurred more than once (source unclear, possibly an earlier accidental `sudo git`/`sudo make` invocation). Fix (tmux ops pane, sudo required): `sudo chown -R kpihx:kpihx .git/refs/remotes/ .git/logs/refs/remotes/` then re-run the push — check BOTH `refs/remotes/` and `logs/refs/remotes/` in the same pass, they can be root-owned independently (found on `ollama-ipex` 2026-08-27: first chown fixed `refs/`, push still failed on `logs/refs/` until a second chown). Do not assume the remote push failed just because this error appears — always check the line above for `[new branch]`/`->` first.
- GitLab topics via `glab api --method PUT projects/<id> --field topics=a,b`: ONE comma-separated field. Repeating `--field topics=` keeps only the LAST value; `topics[]=` is rejected (400 with allowed-params error). Verified live on `kpihx-labs/proxies/*` (2026-09-05).
- GitLab project transfer (`PUT projects/<id>/transfer --field namespace=...`) is ASYNC: the 200 response still shows the OLD path — re-GET after ~10s to confirm. GitHub repo transfer returns the old name too; verify with `gh repo view <new-path>` (old URLs redirect).
- GitHub orgs are FLAT (no subgroups): moving `kpihx-labs/X` → `kpihx-labs/<subgroup>/X` on GitLab has NO GitHub equivalent — repo stays at `kpihx-labs/X`; mirror the grouping there with topics only.
