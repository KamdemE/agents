## Insights

- Initial baseline created automatically from insights governance standard.
- If `SSH_AUTH_SOCK` points to `$HOME/.bitwarden-ssh-agent.sock` and `ssh-add -l` returns `Error connecting to agent: Connection refused`, the socket path existing is **not** enough: Bitwarden Desktop / its SSH agent is not actually serving yet, so `git push` will still fail with `Permission denied (publickey)`.
- If Bitwarden Desktop is relaunched and `ssh-add -l` / `ssh -T git@github.com` still hang or time out, treat it as an **unlock / approval pending** state rather than a Git problem: do not force HTTPS, and ask the user to unlock/approve Bitwarden before retrying `pull` or `push`.
- `fatal: .git/index: index file open failed: Not a directory`, seen ~1-4 times right as a hook starts (once per submodule): this is `git-hook-passthrough.sh`'s submodule loop (`submodule_dirty_report`/`submodule_push_report`) running `git -C <submodule> ...` while still carrying the hook's inherited `GIT_DIR`/`GIT_WORK_TREE`/etc — a submodule's `.git` is a file, not a dir, so a leaked git-dir path colliding with it hits ENOTDIR. Non-fatal to the actual commit/push (git recovers), but noisy. Fixed 2026-08-26 (v2.10.1) with `unset $(git rev-parse --local-env-vars)` at the top of both functions — the pattern `git help githooks` itself documents for running git against a foreign repo from a hook. Could not force-reproduce it in isolated manual testing even with a faithful relative-`GIT_DIR` simulation — the fix is applied on the strength of the documented mechanism matching the symptom exactly (same error text, same "count = submodule count" pattern as a matching real-world case: github.com/sds/overcommit#383), not on a local repro. If it recurs after this fix, that would mean the mechanism is something else and needs re-investigating from scratch, not a "the fix didn't stick" retry.
- No `ssh-agent` runs by default on `server` (`XDG_SESSION_TYPE=tty`, no GNOME session → the documented `gcr-ssh-agent` "PREFERRED" strategy in `k-ssh/SKILL.md` never actually starts — it's undocumented-as-unwired, not broken). Every git-over-ssh op decrypts the key fresh; the submodule push gate loops per-submodule, so a passphrase-protected key gets prompted once per submodule in the same `git push` (e.g. 4 submodules = 4 prompts back to back) — looks like a bug, is actually just "no caching, N sequential connections". `ssh-add --help` alone failing with "Could not open a connection to your authentication agent" is the fast way to confirm this is the cause before chasing anything else.
- CORRECTION (2026-08-26, partially supersedes the entry above): server NOW has `SSH_AUTH_SOCK=$XDG_RUNTIME_DIR/gnupg/S.gpg-agent.ssh` (gpg-agent serving SSH) — but it starts each session with **no identities** (`ssh-add -l` → rc=1), so the N-prompts behavior persists until one `ssh-add` per boot/session (see k-ssh insights for the updatestartuptty ritual).
- PRE-PUSH GATE FALSE POSITIVES (fixed v2.11.0, commit 2da5e5f): `submodule_push_report()` fed `git ls-remote` stdout+stderr into one string then `cut -f1`, so ANY multi-line server banner (e.g. `remote: INFO: ...`) polluted `remote_sha` → 🔴 "HEAD not on remote/main" for submodules that WERE pushed while their SHAs matched exactly, and connection drops were misreported as mismatches instead of unreachable. Fix: extract only real ref lines via awk `length($1)==40 && $1 !~ /[^0-9a-f]/` + distinct UNREACHABLE / NOT-found / mismatch branches.
- ⚠️ Portability trap hit while fixing the gate: some systems ship mawk WITHOUT ERE interval support — `$1 ~ /^[0-9a-f]{40}$/` silently matches NOTHING (verified live: prints "NO INTERVALS"). Never use `{n}` quantifiers in portable sh/awk; use `length()==N` + negated character class.
- Fast push-failure diagnosis trio (all non-secret): `echo $SSH_AUTH_SOCK` (socket set?) → `ssh-add -l` (identities loaded?) → `ssh -o BatchMode=yes -T git@github.com` (fails fast instead of hanging; distinguishes "no identity" from real network errors).
- `error: update_ref failed for ref 'refs/remotes/<remote>/<branch>': cannot lock ref ... Permission denied` on `git push`/`make push`, even though the log line right above it shows `[new branch] <branch> -> <branch>` (the push itself succeeded remotely): the LOCAL tracking-ref bookkeeping is blocked because `.git/refs/remotes/<remote>/` (and/or `.git/logs/refs/remotes/<remote>/<branch>`) is **root-owned** on a repo that should be entirely user-owned — root ownership on stray files inside an otherwise-user-owned `.git/` has recurred more than once (source unclear, possibly an earlier accidental `sudo git`/`sudo make` invocation). Fix (tmux ops pane, sudo required): `sudo chown -R $USER:$USER .git/refs/remotes/ .git/logs/refs/remotes/` then re-run the push — check BOTH `refs/remotes/` and `logs/refs/remotes/` in the same pass, they can be root-owned independently (found on `ollama-ipex` 2026-08-27: first chown fixed `refs/`, push still failed on `logs/refs/` until a second chown). Do not assume the remote push failed just because this error appears — always check the line above for `[new branch]`/`->` first.
- Selective online update preserving local deletions (workstation 2026-09-10): `git fetch` + `git diff --name-status HEAD..origin/master`, then `git checkout origin/master -- <paths>` ONLY for paths whose parents still exist locally; skip anything under locally-deleted dirs; `git rm` upstream-D paths that still exist locally; renames = `git rm <old>` + checkout `<new>`; typechanges checkout cleanly. Files modified on BOTH sides need hunk-level union (never blind checkout): keep machine-policy hunks (model IDs, `~` paths), import capability hunks (providers, plugins, key tables). Result stays uncommitted (staged incoming + unstaged local) — commit only on explicit request.
- Parallel operator work hazard (workstation 2026-09-10): the operator purged files (skill dirs, references) in parallel while the agent ran bulk edits — files vanished mid-task (one dir never hit trash). Defenses: before any bulk/sweep step, snapshot `git status --short` counts; re-verify a file exists immediately before Read/Edit (never assume the earlier Glob still holds); keep destructive tmux panes (nvim/Oil) CLOSED while sending keys elsewhere — stray keystrokes into an Oil buffer can create/rename real files (junk dir incident, trashed). When files disappear that no agent command explains, STOP bulk work and ask the operator before continuing.
