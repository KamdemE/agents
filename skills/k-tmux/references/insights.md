# k-tmux Insights

Purpose: autonomous runtime memory for this skill domain to avoid repeated mistakes, repeated dead-end searches, and repeated ineffective action patterns.

## Governance

- Read this file before non-trivial work in this skill domain.
- Update this file at the end of the task whenever a durable insight is learned.
- Keep entries concise, actionable, and focused on anti-repeat value.
- Reorganize, merge, or prune stale entries autonomously to keep signal high.

## Insights

- Initial baseline created with skill v1.0.0.
- KπX tmux config lives at `$HOME/.tmux.conf` (canonical). Skill asset `assets/tmux.conf` is a symlink — edit the real file, then `tmux source-file ~/.tmux.conf`.
- Without explicit wheel bindings, mouse scroll at the shell prompt can reach zsh as ↑/↓ and browse command history instead of scrolling the tmux buffer. The bundled config forces copy-mode scroll on wheel up.
- `copy-mode -e` auto-exits copy mode when scrolling back to the bottom — preferred over plain `copy-mode` for daily use.
- **`sui` deprecated (2026-05-18):** critical shell = shared tmux only; full gate in `k-tmux/SKILL.md` → Shared interactive gate.
- Poll **≥30s** after `send-keys` before chat handoff; give full attach + command + what KπX must type only after that. Earlier versions (pre-2026-05-29) caused a **chat handoff too early** — agent stopped mid-turn instead of looping until >=30s or command completion. Fix: loop every 3-5s, check for shell prompt (done) vs password prompt (keep polling). Only chat after >=30s without progress.
- **Cleanup is mandatory (2026-05-29):** every temp session/window created for a sudo/SSH gate MUST be killed after the command finishes and verification passes. `tmux kill-session -t NAME`. No mess, no dangling windows. If KπX detaches without finishing, the session stays available — but once the task is verified complete, the agent must auto-clean.
- **NEVER split panes for sudo (2026-05-29):** creating a pane split in the user's current window destroys their layout and can kill their active editor (micro, vim, etc). Always use `tmux new-window -t <SESSION> -n <name>` — a full new window. After the command finishes, kill the window and select-window back to the previous one.
- **15s password poll rule (2026-05-29, updated to 15s):** after sending a sudo command, poll every 3-5s for ≥15s before any chat handoff about the password. If KπX enters the password within that window, keep polling until the full command finishes. Only ask if ≥15s pass with no password input. After the command finishes (shell prompt visible), kill the window and return to previous window.
- Reuse short-named sessions/windows; create/kill only when necessary for clarity.
- `tmux-resurrect` owns save/restore contents; `tmux-continuum` schedules auto-save/auto-restore and can also provision a user-login `systemd` tmux service via `@continuum-boot on`.
- Resurrect shell-history restoration is removed upstream; arrow-key history remains a zsh concern, not a tmux persistence feature.
- **`𝛱/live` dev session (2026-05-24):** use tmux session `live` — window `ops` for `make check`/git; `brain` for `make dev-brain` (:8000); `web` for `make dev-web` (:5173). Map: `$HOME/KpihX-Labs/𝛱/live/docs/DEV_WORKFLOW.md`.
- **Mouse copy (2026-05-25, v1.4.4):** with `mouse on`, OS/terminal selection does not work on drag; **Shift+drag does nothing** in Cursor/Zed integrated terminals (tmux keeps the mouse). KπX fix: `mode-keys vi` + `MouseDrag1Pane` → `copy-mode -M` + release → `copy-pipe` (`xclip` / `wl-copy`). **Wheel up** still scrolls buffer. Right-click → copy-mode (no popup menu). Wayland: install `wl-clipboard` if clipboard empty. Keyboard fallback: `Ctrl-a [` → `v`/`y` or `Ctrl-a ]` paste tmux buffer.
- **Persistence reboot (2026-05-25):** saves under `$HOME/.tmux/resurrect/` are working (autosave + manual). Auto-restore runs **only once per new tmux server** (`@continuum-restore on`). `@continuum-boot` + `tmux.service` starts server at login with `new-session -d`; **ExecStop save.sh often fails** (`no server running`) because server is already gone before stop — do not rely on shutdown save. If login boot starts server before restore window, or user starts a second server, restore is skipped. Last-good workflow before reboot: `Ctrl-a Ctrl-s`, check `ls -l ~/.tmux/resurrect/last`. After reboot if empty: `Ctrl-a Ctrl-r`.
- **Reboot forensics (2026-05-25):** `journalctl --user -u tmux.service` showed **ExecStop save.sh → `no server running`** and login server dying in ~2s. **Fix applied:** `@continuum-boot off` in `$HOME/.tmux.conf`, `systemctl --user disable --now tmux.service`. Post-login: run `tmux` once from a real terminal → `@continuum-restore` runs. Runbook: `k-tmux/SKILL.md` → **First tmux after reboot (post-login)**. Good historical save example: `tmux_resurrect_20260524T185451.txt` (`live` + `default`).
- **CRITICAL — Always identify pane before send-keys (2026-06-05):** sent `:qa!` to wrong pane (opencode default session) instead of actual nvim pane. Must run `tmux list-panes -a -F '#{session_name}:#{window_index}.#{pane_index} #{pane_current_command}'` first to confirm exact target. Rule added to SKILL.md under "Send Keys & Capture Output".
- **Sudo gate with `sudo systemctl` + `apt purge` via `ubuntu:0.2` (2026-07-21):**
  - Pane `ubuntu:0.2` (zsh) is the designated sudo/ops pane — works well.
  - `sudo apt purge` can stall if the apt solver hangs on unresolvable dependencies. Always pre-check reverse-depends before `apt purge -y "libvirt-*"`: `apt-cache rdepends --installed <pkg> | grep -v libvirt`.
  - For complex purges, send the full command as one `send-keys` (no split between disable + purge) to avoid KπX seeing an intermediate prompt.
  - `tmux capture-pane -t SESSION:WIN.PANE -p -S -` to capture full scrollback when output is long (polling with `tail -10` is sufficient for progress).
- **When told "make it a reflex / no legacy", grep the WHOLE cross-referenced set, not just the section you already touched (2026-08-16):** the `TMUX_TIMEOUT`/`TMUX_LINES` stateful pattern was validated and partly implemented (param parsing + registry in `tmux-notify.js`), but a first pass left `k-tmux/SKILL.md` with 2 legacy sections (`### Run and poll`, `## Send Keys & Capture Output`) still instructing manual `capture-pane` loops — directly contradicting the very reflex just introduced — and `rules/tool-discipline.md` scoped the reflex to `sudo` only instead of ANY `tmux send-keys`. Anti-repeat: when a new behavioral reflex is introduced, `rg` for the OLD pattern's keywords (`capture-pane`, `poll`, `loop`) across the owning skill's `SKILL.md`, cross-referenced rule files (`rules/*.md`), and any plugin inventory (`scripts/plugins/AGENTS.md`) BEFORE declaring the change "documented" — a half-updated doc is worse than an undocumented one because it actively teaches the contradictory behavior in the untouched half.
- **Prose-only reflexes get exploited via loopholes — a LIVE agent proved it (2026-08-16):** right after the doc pass above, KπX caught a real agent send a correct `TMUX_TIMEOUT=20 TMUX_LINES=15 tmux send-keys ... 'sudo apt update'`, then IMMEDIATELY run a manual `tmux capture-pane` anyway, self-justifying it as a "one-shot inspection" — a phrase LITERALLY lifted from the just-updated `SKILL.md` (which allowed manual capture-pane "when KπX explicitly asks"). The agent stretched an exception meant for KπX-initiated requests into self-initiated "just checking" behavior. Root cause #2: `k-opencode/references/terminal-consciousness.md` (linked from `k-opencode/SKILL.md` References) teaches a general "send-keys → capture-pane → iterate" self-observation loop without excluding "waiting for a long command" as a case. **Anti-repeat rule: any reflex meant to eliminate an anti-pattern MUST be technically enforced (a blocking `tool.execute.before` hook, same pattern as `make-check-guard.js`), not just documented — prose alone WILL be reinterpreted/loopholed by a model under plausible-sounding self-justification, even a capable one.** Fix applied: `tmux-notify.js` now `throw`s on any `tmux capture-pane` targeting a pane with a pending registry entry (see `k-opencode/references/insights.md` same date for the code-level lesson).
- **KπX REVERSED the block above the same day (2026-08-16) — never intercept an agent's diagnostic fallback tool:** after the fix above, KπX explicitly rejected the `throw`-on-`capture-pane` approach: "on n'influence jamais un capture-pane (l'agent peut en avoir besoin si notre plugin dysfonctionne!!) jamais on intercepte de capture-pane!" — i.e. blocking `capture-pane` removes the agent's ONLY way to self-diagnose if `tmux-notify.js` itself breaks (log not written, watcher stuck, registry desync). **New design principle: enforce a reflex PROACTIVELY (inject guidance at the moment of the triggering action) rather than REACTIVELY (block the tempting follow-up action)** — especially when the follow-up action is also the operator's safety-net for the enforcement mechanism's own failure modes. Concretely: the `throw` guard was removed from `tool.execute.before`; a `<tmux-armed>` reminder is now appended via `tool.execute.after` directly to the `send-keys` call's own result, fired for EVERY stateful send-keys (with or without explicit `TMUX_TIMEOUT`/`TMUX_LINES` — defaults still arm it). Anti-repeat: before hard-blocking any agent tool call as an enforcement mechanism, ask "is this the agent's fallback if MY enforcement mechanism itself fails?" — if yes, prefer a nudge over a block.
- **A 3rd root cause found by reading a live agent's OWN self-justification (2026-08-16) — grep for the OLD anti-pattern's keywords across EVERY file that shapes agent behavior, not just the skill/rule files already touched:** KπX asked the agent directly "pourquoi as-tu fait capture-pane?" and it answered with its actual reasoning: *"the rule in AGENTS.md/k-tmux for any elevation... send-keys → poll the pane ≥30s → confirm completion... 'verify the persisted result yourself'."* That phrasing is a near-verbatim quote of `rules/tool-discipline.md` → `## Solo End-to-End Execution (PERMANENT DIRECTIVE, 2026-08-12)`: *"HITL is the sole interaction exception: launch the real approved flow in tmux, **keep polling its pane**, then resume the lifecycle and **verify the persisted result yourself**."* This directive predates ALL the tmux-notify work and was NEVER touched during the entire saga (it lives outside the "tmux sudo Gate" section that had already been fixed twice). `agents/Agent/prompt.txt` (the dedicated end-to-end solo agent, one of `tmux-notify.js`'s `TARGET_AGENTS`) had the SAME residual pattern in 3 separate lines: "poll until completion", "poll ≥30s", "poll with renewable sleeps". **Anti-repeat: when hunting a behavioral anti-pattern's sources, `rg` the OLD keyword across the ENTIRE `.agents/` tree (`rules/*.md`, EVERY `agents/*/prompt.txt`, not just the skill files where the feature "lives") — a PERMANENT DIRECTIVE dated before the new reflex existed is exactly the kind of file that gets forgotten because it doesn't have "tmux" in its section header.**
- **A single global `pending` queue is a session-isolation bug waiting to happen (2026-08-16, found via KπX's direct question "chaque agent dans sa session n'est notifié que pour ce qu'il a lancé ?"):** `tmux-notify.js`'s `chat.message`/`session.idle` handlers used to drain ONE flat `pending: string[]` array regardless of which session triggered the event — if the immediate flush after arming failed/was delayed (network error, session not yet resolvable), the notification sat in the global array with no owner tag, and the NEXT session/agent to send ANY message or go idle would receive it, even if it was a completely unrelated task. Fix: `pending` became a `Map<sessionID, string[]>`; every push/read is keyed by the OWNING `sessionID` captured at arm time (`entry.sessionID`, guaranteed non-null per the `ToolContext` type — `sessionID: string`, not optional). Anti-repeat: any plugin-level queue shared across multiple concurrent OpenCode sessions/agents must be keyed by session id from the very first line of code — a flat array "because there's usually only one active session" is a latent cross-agent leak.
- **A silent-drop code path has ZERO log trace even under debug mode — verify by reading the actual matching branch, not just the doc prose (2026-08-16, found while diagnosing "l'agent n'a pas été notifié" for a sudo run in `ubuntu:0.2`):** `tmux-notify.js`'s log watcher does `const entry = registry.get(ev.pane); if (entry) {...}` — there is NO `debug()` call in the implicit `else` branch when a `prompt` event arrives for a pane that was never armed. This means a `prompt` event for an unarmed pane leaves **zero trace anywhere**, even with `TMUX_NOTIFY_DEBUG=1` set — the doc-described mechanism ("Stateful Integration") is accurate about the happy path but silent about this failure mode. Root cause confirmed: arming ONLY happens in `tool.execute.before` when `input.tool === "bash"` and the command matches `tmux send-keys ... -t <target>` — a command typed DIRECTLY into an attached tmux pane (human, not an agent's `bash` tool call) never arms the registry, so the pane's `precmd` hook still fires and writes to `/tmp/tmux-pane-done.log` correctly, but the notification is silently dropped. Anti-repeat: when diagnosing "notification didn't fire", always read the actual `if (entry) {...}` / matching branch in the watcher code — the `debug()` calls document only what the ORIGINAL author thought was worth logging, not every branch that can silently short-circuit.
- **Live tmux server state can drift silently from the config file on disk — always check BOTH (2026-08-16, found while diagnosing "exit in a pane leaves it visible dead, no layout reflow" — KπX explicitly said this used to work differently):** `assets/tmux.conf` had NO `remain-on-exit` line (confirmed by reading the full file), yet `tmux show-window-options -g` showed `remain-on-exit on` live. Root cause: `remain-on-exit on` was deliberately set during the v1.14.0 tmux-notify pass (dead panes stayed readable via `capture-pane` under the older pane-died/exit-code architecture) and later removed from the config file once the design moved to the `precmd`/prompt-event mechanism (which the doc now correctly states doesn't need it) — but **sourcing an edited config file only APPLIES what's newly present in it; it never unsets an option that was REMOVED from the file.** The live server had silently carried the stale `on` setting for the rest of the day, invisible to anyone reading `tmux.conf` alone. Fix applied: `tmux set-window-option -g remain-on-exit off` + `tmux set-window-option -gu remain-on-exit-format` (live, non-destructive, no restart needed). Anti-repeat: whenever a tmux behavior contradicts what the config file says (or what you remember as "before" behavior), check the LIVE server state with `tmux show-options -g` / `tmux show-window-options -g` — never assume the config file on disk is what's actually running; any option ever explicitly `set`/`set-window-option`'d persists across config edits until it is explicitly unset or the server restarts.
- **opencode web's embedded terminal spawns an isolated PTY that generic shell-startup logic can accidentally hijack — check the tool's own source for a distinguishing env var before writing exceptions (2026-08-16, found via KπX report "opencode web terminal ça bug"):** `kshrc.base`'s Auto-tmux block (`if [ -z "$TMUX" ] && ... && [ -t 0 ]; then tmux attach ...`) fires on ANY interactive shell with a real TTY and no `$TMUX` — which includes opencode web's own terminal panel PTY (confirmed via `packages/opencode/src/pty/index.ts` on GitHub: it's a genuine `bun-pty` spawn, real TTY, meant to be an isolated session streamed 1:1 to the browser via WebSocket `Pty.Service`). Without an exception, that isolated PTY got hijacked into the SAME shared desktop tmux session — multi-client resize glitches, input cross-contamination (web-panel keystrokes landing on whatever pane is active elsewhere), and since the Auto-tmux `tmux attach` call is a plain child (not `exec`'d), a detached PTY leaves the underlying zsh process alive and idle, plausibly compounding the known upstream leak `anomalyco/opencode#19225` ("opencode web leaks hundreds of idle /bin/zsh PTYs"). Fix: opencode sets `OPENCODE_TERMINAL=1` UNCONDITIONALLY on every PTY it spawns for its terminal feature (confirmed straight from source) — the exact signal needed. Added `[ -z "$OPENCODE_TERMINAL" ]` to the Auto-tmux guard in `kshrc.base` + all 7 infra copies. Anti-repeat: before writing a shell-startup exception for "app X's embedded terminal", check the app's own source/docs for an env var it sets on its spawned PTYs FIRST — most modern terminal-embedding tools (VSCode's `TERM_PROGRAM`, opencode's `OPENCODE_TERMINAL`, etc.) already expose this distinguishing signal; don't guess at parent-process detection when a documented/source-confirmed env var exists.
- **`tmux split-window -t <SESSION>:<WINDOW>` (window-only target) splits the WHOLE window, not the intended single pane — confirmed the hard way (2026-08-26, deep-pc6, KπX reaction: "putain le pane 0 est cassé"):** after `kill-pane`-ing the standard 3-pane `agents` window's ops pane (index 2), a recreate attempt ran `tmux split-window -t deep-pc6:0 -v` (target = window `deep-pc6:0`, no `.pane` suffix) — this split relative to whatever the CURRENTLY ACTIVE pane happened to be inside that window, silently resizing/relocating panes 0 (opencode) and 1 (nvim) that were never meant to move. `k-tmux/references/session-layout.md`'s own documented setup commands are unambiguous about this and were simply not re-read before acting: `tmux split-window -h -t <equip>:agents.0` (split explicitly FROM pane 0) then `tmux split-window -v -t <equip>:agents.1` (split explicitly FROM pane 1) — always target `WINDOW.PANE`, never bare `WINDOW`, when the intent is "add a pane next to THIS specific pane." **Recovery sequence that worked without touching the live opencode/nvim processes:** (1) `tmux kill-pane` the broken/extra pane only; (2) `tmux move-pane -h -s <window>.<nvim-pane-index> -t <window>.<opencode-pane-index>` — moves an existing pane to a new position as a horizontal split next to a target pane, preserving its running process untouched (does NOT kill/restart nvim); (3) `tmux split-window -v -t <window>.<nvim-new-index> -c ~/KpihX-Labs` — now correctly scoped to just that one pane's real estate. Verify geometry with `tmux list-panes -F '#{pane_index} #{pane_id} #{pane_current_command} #{pane_left},#{pane_top} #{pane_width}x#{pane_height}'` before AND after any layout surgery — comparing exact `left,top WxH` numbers against the target diagram is the only reliable way to confirm a fix, prose description of "looks right" is not enough. Anti-repeat: before ANY `tmux split-window`/`move-pane`/`kill-pane` touching a session that has live agent/editor panes (`opencode`, `nvim`), read `k-tmux/references/session-layout.md` FIRST for the exact target geometry and copy its `-t <window>.<pane>` targeting pattern verbatim — never freehand a tmux layout command from memory on a shared, already-populated window.
- **A `pinentry` process can spin at 70-95% CPU holding gpg-agent's pinentry lock instead of rendering its dialog (2026-08-26, deep-pc6, cross-ref `k-ssh/references/insights.md` same date):** twice in one session, a freshly spawned `pinentry` (traced via `ps aux | grep pinentry`) burned significant CPU for several minutes while `journalctl --user -u gpg-agent` repeated `failed to acquire the pinentry lock: Timeout`. `kill -9 <pid>` immediately unblocked a fresh, correctly rendering `pinentry` dialog on the very next `ssh-add`/`ssh -T` attempt. This is an SSH-agent/gpg-agent-layer issue, not a tmux-layer one, but it manifests INSIDE a tmux pane (looks like the pane is "frozen" — nothing renders, `capture-pane` shows a blank/stale screen) and can be mistaken for a tmux/pty bug. Diagnostic reflex: if a `tmux send-keys`-launched `ssh`/`git`/`ssh-add` command hangs with a suspiciously blank pane, check `ps aux | grep pinentry` for a high-CPU zombie BEFORE assuming the tmux pane itself is broken.
- **tmux plugins that "own" a key (grep-based or unconditional rebind) silently overwrite manual `bind` lines on EVERY `tpm` reload — check `references: helpers.sh`/plugin source BEFORE manually binding a key a plugin might also manage (2026-08-26, deep-pc6, KπX clipboard debugging saga):** `tmux-copycat`'s `scripts/copycat_mode_bindings.sh` → `copycat_quit_copy_mode_keys()` does `tmux list-keys -T copy-mode-vi | grep "cancel" | awk '{print $4}'` — i.e. it dynamically auto-detects and wraps EVERY copy-mode-vi key whose bound action contains the literal substring `"cancel"` (e.g. `copy-pipe-and-cancel`, `copy-selection-and-cancel`) with its own `copycat_mode_quit.sh` chain, **every single time `tpm` runs** (last line of `tmux.conf`, always after any manual `bind` earlier in the file). This is NOT configurable via any exposed tmux option — it's a hardcoded grep, so ANY manual binding using an `-and-cancel` action on `y`/`Enter`/`MouseDragEnd1Pane` gets silently re-wrapped, and repeated `tmux source-file` reloads COMPOUND the wrap (each pass captures the ALREADY-wrapped command and wraps it again — confirmed by decoding an embedded base64 blob inside a "corrupted" `Enter` binding that turned out to be a stale snapshot of an UNRELATED key's `list-keys` line, proving the capture-then-rewrap cycle). Separately, `tmux-yank` (`yank.tmux` + `scripts/helpers.sh`) does the SAME unconditional-rebind-on-reload for `y`/`MouseDragEnd1Pane`/`M-y` (`yank_key_default="y"`, `yank_with_mouse_default="on"`) — but unlike copycat, it exposes TWO supported customization hooks precisely for this: `@override_copy_command` (the shell command used when the action is a `copy-pipe*` variant) and `@yank_action` (`yank_action_default="copy-pipe-and-cancel"` — can be set to `"copy-selection"`/`"copy-selection-and-cancel"` to use tmux's fully NATIVE clipboard mechanism instead, zero external command, `set-clipboard on` handles OSC52 relay internally). **Anti-repeat: before manually `bind`-ing ANY key in a table also touched by an installed plugin, `grep`/read that plugin's own `.tmux`/`scripts/*.sh` source for (a) which keys it claims and (b) whether it exposes a supported override option — use the plugin's own hook, never fight it with a competing manual `bind`, since `tpm` always re-applies plugin bindings LAST on every reload regardless of file order.** Also confirmed: removing a plugin from `@plugin` (or unsetting a `set -g @option`) in the FILE does not retroactively clean already-applied LIVE bindings/option values on the running server — `tmux unbind-key -T <table> <key>` (for bindings) and `tmux set-option -gu <option>` (for options) are needed to fully reset stale state, same lesson as the `remain-on-exit` entry above.
