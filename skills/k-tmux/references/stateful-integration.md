# Stateful Integration (Agent → Tmux → Agent)

This reference documents the detailed mechanism and architecture for notifying agents when a persistent tmux pane returns to its shell prompt.

## Stateful Integration Mechanism

An agent (e.g. an OpenCode plugin) can be **notified** when a **persistent pane** returns to its shell prompt (a command the agent launched finished) — instead of the agent polling `capture-pane`. Panes PERSIST: nothing is killed or detached, no `remain-on-exit` needed, and no tmux-side silence heuristics are used. Five pieces cooperate:

1. **Shell prompt hook** (in `.kshrc`, propagated to all infras): a `precmd` (zsh) or `PROMPT_COMMAND` (bash) hook writes a JSON `{"event":"prompt","pane","ts"}` line directly to `/tmp/tmux-pane-done.log` whenever the shell prompt redraws. This avoids false positives during silent waits (e.g. `sudo` password prompts).
2. **`k-opencode` `tmux-notify.js` — arming (`tool.execute.before`) + proactive reminder (`tool.execute.after`):**
    - `tool.execute.before` intercepts any `bash` tool call containing `tmux send-keys -t <target> ...`, parses `TMUX_TIMEOUT=<seconds>` (default `30`) and `TMUX_LINES=<n>` / `TMUX_MAX_LINES=<n>` (default `50`). It creates a **pane lease**: an exclusive completion watch owned by the launching OpenCode session.
    - A lease is **not** an input lock. Its owner may send arbitrary follow-ups, corrections, or `Ctrl+C` to an active pane; these are control input and never replace the original watch. A different OpenCode session is blocked. A new watched command is armed only after the original `<tmux-notify>` releases the lease; this avoids treating tmux's brief pre-execution shell state as a completed command. Prompt timestamps prevent an old event in the log from completing a later lease.
    - The watcher polls `/tmp/tmux-pane-done.log`; on a timestamp-matching shell `prompt` event it captures the last `TMUX_LINES` lines and injects definitive `<tmux-notify>` (the ONLY stop condition). Every `TMUX_TIMEOUT` period while the pane has not returned to the shell emits a recurring `<tmux-watchdog>` snapshot and re-arms until shell return — no mode flag, single simple rule.
3. **Session isolation** (fixed 2026-08-16, real bug found): pending notifications are queued in a `Map<sessionID, string[]>`, NEVER a flat global array. Delivery via `chat.message`/`session.idle` ONLY ever drains the bucket owned by the exact session receiving the event — a notification armed by agent/session A can never leak into agent/session B's conversation, even if A's immediate flush was delayed or failed.
4. **Pane lease isolation — owner-aware, not a blanket busy lock**:
    - **Tracked lease:** an unresolved lease blocks `send-keys` from every *other* OpenCode session, preventing cross-agent input contamination and the historical "last-arm-wins" overwrite.
    - **Owner control:** the session that created the lease may continue an interactive TUI, adjust a prompt, or cancel with `Ctrl+C`. Its input does not create a second lease or reset the original timer.
    - **Untracked busy pane:** when no lease exists, `pane_current_command` must be an idle shell (`zsh`/`bash`/`sh`/`fish`) before a new lease is armed. This protects processes started by KπX or outside the plugin.
    - `capture-pane` is never blocked. It is a diagnostic fallback for a broken watcher and an explicit snapshot tool for a live TUI; only repeated polling of a normal shell-returning command remains prohibited.
5. **Timeout self-adjustment — no pane interaction, ever (2026-08-29)**: a watchdog repeating on the same interval with an unchanging message left the agent unclear on what to do, and there was no way to widen the interval short of `send-keys`-ing text into the pane (would pollute the stdin of whatever is actually running there). Fixed with a pure META marker recognized on the agent's OWN bash command (never a `send-keys` call, never delivered to the pane): `: TMUX_ADJUST <pane> <seconds>` (`:` is the bash no-op builtin — always succeeds, zero side effects). `tool.execute.before` matches it anchored on the whole trimmed command (deliberate-only, never an accidental substring inside a script), and if the calling session owns the lease, updates `timeoutSecs` in-memory, clears+re-arms the watchdog (countdown restarts from the new value), and resets the escalation counter (`watchdogCount`). Denied for another session's lease, a harmless no-op if the pane isn't (or is no longer) leased — never a hard error either way, `tool.execute.after` always answers with a `<tmux-timeout-adjusted>` confirmation. The watchdog message itself (`notificationFor()` in `tmux-notify.js`) now carries `watchdogCount` and escalates: checks 1–2 offer "continue in parallel, or adjust if you expect longer"; checks ≥3 read "genuinely long-running, not stuck" and push adjusting the interval or aborting via `Ctrl+C` — every message states the exact adjust syntax so the agent never has to guess it.

## Rules for Agents

The reminder is a **reflex**, not an opt-in — every `tmux send-keys` gets armed AND reminded, whether or not you added `TMUX_TIMEOUT`/`TMUX_LINES` (defaults apply). You never manually `capture-pane` in a loop to check progress — but if an automatic final capture is empty, incomplete, or insufficient, immediately run the prescribed one-shot diagnostic capture `tmux capture-pane -p -t <pane> -S -100` and use it.
