# Stateful Integration (Agent → Tmux → Agent)

This reference documents the detailed mechanism and architecture for notifying agents when a persistent tmux pane returns to its shell prompt.

## Stateful Integration Mechanism

An agent (e.g. an OpenCode plugin) can be **notified** when a **persistent pane** returns to its shell prompt (a command the agent launched finished) — instead of the agent polling `capture-pane`. Panes PERSIST: nothing is killed or detached, no `remain-on-exit` needed, and no tmux-side silence heuristics are used. Four pieces cooperate:

1. **Shell prompt hook** (in `.kshrc`, propagated to all infras): a `precmd` (zsh) or `PROMPT_COMMAND` (bash) hook writes a JSON `{"event":"prompt","pane","ts"}` line directly to `/tmp/tmux-pane-done.log` whenever the shell prompt redraws. This avoids false positives during silent waits (e.g. `sudo` password prompts).
2. **`k-opencode` `tmux-notify.js` — arming (`tool.execute.before`) + proactive reminder (`tool.execute.after`):**
   - `tool.execute.before` intercepts any `bash` tool call containing `tmux send-keys -t <target> ...`, parses `TMUX_TIMEOUT=<seconds>` (SECONDS — NOT milliseconds; default `300` = 5 min.) and `TMUX_LINES=<n>` / `TMUX_MAX_LINES=<n>` (default `20`) from the command string — applying these defaults EVEN IF the agent didn't add the vars, so EVERY stateful send-keys gets armed — resolves `<target>` to a pane id, and arms an in-memory registry entry with an unref'd `setTimeout`.
   - `tool.execute.after` runs right after that SAME send-keys command has actually executed, and appends a `<tmux-armed>` reminder DIRECTLY to the tool call's own result text (no round-trip through the conversation): "pane armed, do not capture-pane, continue a parallel task or stop, you will be auto-notified." **This is the reflex enforcement mechanism** — it replaces an earlier REACTIVE `throw`-based block on `capture-pane` itself, which was explicitly REMOVED (KπX, 2026-08-16): `capture-pane` is NEVER intercepted, because the agent may legitimately need it as a manual fallback if this very plugin malfunctions (log not written, watcher stuck, registry desync) — blocking the one diagnostic tool available in that failure mode would be worse than the anti-pattern being prevented.
   - The log watcher polls `/tmp/tmux-pane-done.log`; on a matching `prompt` event it clears the timer, runs `tmux capture-pane`, slices the last `TMUX_LINES` lines, and injects a `<tmux-notify>` message into the OpenCode session (`client.session.prompt`) whose label states the EXACT number of lines shown (e.g. `Last 20 output lines:`) — never a vague placeholder. If `TMUX_TIMEOUT` elapses first, ONE "still running" notification fires with a fresh capture, but the registry entry is kept alive (only its timer is cleared) so the real completion notification still fires automatically later.
3. **Session isolation** (fixed 2026-08-16, real bug found): pending notifications are queued in a `Map<sessionID, string[]>`, NEVER a flat global array. Delivery via `chat.message`/`session.idle` ONLY ever drains the bucket owned by the exact session receiving the event — a notification armed by agent/session A can never leak into agent/session B's conversation, even if A's immediate flush was delayed or failed.
4. **Busy-pane block — TWO cascading layers** (layer 1 added 2026-08-16, KπX directive — "on demande d'utiliser un autre pane vide si présent, ou en créer un si tous occupés"; layer 2 added same day, KπX follow-up question "tu check juste busy par un autre agent ou vrai busy ?"):
   - **Layer 1 — tracked-busy**: `tool.execute.before` REJECTS a `tmux send-keys` targeting a pane that already has an unresolved registry entry (a previously armed command that hasn't returned to its prompt yet). Before this layer existed, a second arm on the SAME pane silently overwrote the first ("last-arm-wins") — the first session would never be notified, with zero trace anywhere, even in debug logs (a real gap found the same day via a direct KπX question about session isolation).
   - **Layer 2 — untracked-busy**: layer 1 alone only catches panes WE armed via our own `tmux send-keys` interception — a pane busy for any OTHER reason (KπX typing directly in it, an agent bypassing our interception, a leftover foreground process) was invisible to it. If layer 1 finds nothing, `tool.execute.before` now ALSO queries `tmux display-message -p -t <paneId> '#{pane_current_command}'` (pure metadata, no `capture-pane`/content read needed) and blocks if the result isn't one of `zsh`/`bash`/`sh`/`fish` — a real, independent ground-truth signal that catches genuine busyness regardless of whether our system ever tracked it.
   - Either layer's `throw`d message tells the agent EXACTLY what to do: **never send-keys into an occupied pane — use a different EMPTY pane if one exists (`tmux list-panes -a`), or create a new pane/window if all are occupied.** Same `throw`-to-block pattern as `make-check-guard.js` (the only other hook in this kernel that blocks a tool call outright) — this is a DIFFERENT scope from the `capture-pane` block that was removed in point 2: blocking `send-keys` into a busy pane protects against input cross-contamination; blocking `capture-pane` would have removed the agent's only diagnostic fallback, which is why that one stays unblocked.

## Rules for Agents

The reminder is a **reflex**, not an opt-in — every `tmux send-keys` gets armed AND reminded, whether or not you added `TMUX_TIMEOUT`/`TMUX_LINES` (defaults apply). You never manually `capture-pane` in a loop to check progress — but `capture-pane` itself is always available to you as a diagnostic fallback if you suspect the plugin isn't working.
