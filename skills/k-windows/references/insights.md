# k-windows — Insights

Durable, evolutionary lessons for this skill domain. Read before non-trivial work; append at task end.

- **2026-08-25 — Windows-side agent knowledge can live for months with zero git history:** the Windows-side `.agents/skills/{k-windows,k-win-msys2,k-dxo}` this skill was migrated from had never been `git init`'d — real risk of total loss (disk failure, accidental delete) for genuinely deep, hard-won knowledge (an MSYS2 HOME-resolution saga, a Developer Mode symlink incident, months of de-bloat history). Anti-repeat: any `.agents`-pattern knowledge base found without a `.git` directory is a rescue priority, not a "nice to have someday" — check for it explicitly (`ls -la <path>/.git`) rather than assuming a `.agents/` folder is automatically version-controlled just because the WSL kernel convention says it should be.
- **2026-08-25 — Windows can't reliably symlink back into a WSL-side canonical copy:** unlike WSL-side infra kshrc files (which ARE symlinked from `~/.agents`), MSYS2/Windows-native config files (`.zshrc`, `.tmux.conf`, `nsswitch.conf`, PowerShell profile) stay as real, separately-maintained files on the Windows/MSYS2 filesystem. The kernel's `assets/msys2/` here is a **documented, versioned copy** for reference/recovery — intentional duplication, not a live-symlink target. Don't try to force the WSL "single canonical copy + symlink" pattern across the Windows/WSL filesystem boundary; it doesn't cross cleanly (Developer Mode requirement, plus MSYS2's own filesystem is not the same namespace WSL sees under `/mnt/c`).
- **2026-08-25 — A machine-specific infra skill can become just as disposable as a company-specific one — audit for generalizable content in BOTH, not just the company skill:** the first migration pass correctly kept DxO-internal facts out of `k-laptop` (hardware/de-bloat skill) and generic facts out of `k-dxo` (company skill) — but missed that `k-laptop` itself will be abandoned at internship end too, since the laptop belongs to DxO, not the user. A follow-up re-audit found 4 genuinely reusable techniques (stubborn-service disable, silent software uninstall, RDP/Chrome-Remote-Desktop enable, dual-GPU idle mitigation) that were sitting only in that machine's de-bloat scripts — reusable at any future employer/laptop, but invisible until someone asked "what happens to THIS skill specifically when the laptop is gone too?" Anti-repeat: when a "machine skill" exists for hardware that isn't the user's own property, always ask which of its contents are hardware-model-specific (fine to lose) vs. general Windows-admin technique (must be pushed up to `k-windows`) — the ownership question, not just the company-secrecy question, is what determines what's actually safe to lose.
- **2026-08-25 — Contradictory historical docs: keep the resolution, not both sides:** the Windows-side migration source had 3 different, mutually-contradictory tmux session/window maps across `SKILL.md` prose, an older `bootstrap_tmux.ps1` snapshot, and the canonical (symlinked, newer) `tmux-sessions.ps1`. Rather than preserving all three as "history," the fix here replaced the MSYS2-tmux example with one clean, DxO-agnostic, machine-agnostic script (session `windows`, windows `agents`/`default`/`tmp`, mirroring `k-tmux`'s standard 3-window equipment layout exactly) — because this skill is generic (not tied to one machine's specific historical session names), preserving the old contradictory names here would have been actively misleading, not "more complete."
- **2026-08-26 — `Get-Service sshd` ≠ `Get-WindowsCapability -Online -Name OpenSSH.Server*`, verified live on a corporate-imaged machine:** the service showed `Running`/`Automatic` while the Capability query showed `NotPresent` on the exact same box — two independent tracking systems (Service Control Manager vs. DISM/CBS Feature-on-Demand state). Corporate images frequently deploy OpenSSH outside the FOD mechanism (golden-image bake, MSI, SCCM/Intune) — the Capability query lied about absence while the service worked perfectly. Anti-repeat: always trust `Get-Service <name>` as the functional ground truth before concluding a Windows feature isn't installed; a `NotPresent` Capability alone is not proof.
- **2026-08-26 — Firewall rule lookups by assumed short name can false-negative:** `Get-NetFirewallRule -Name sshd` (or `netsh ... name=sshd`) found nothing on a machine whose real, working rule was registered under the *display* name `OpenSSH Server (sshd)` — a different string entirely. Always search broadly first (`Get-NetFirewallRule | Where-Object DisplayName -match 'ssh'`, or `netsh advfirewall firewall show rule name=all | findstr /i ssh`) before concluding a rule is missing and creating a duplicate.
- **2026-08-26 — AppLocker can block `pwsh.exe` (PowerShell 7) while leaving `powershell.exe` (5.1) untouched, on a session with a fully High-integrity token:** confirmed via `whoami /groups` showing `Mandatory Label\High Mandatory Level` in the exact same SSH session where `pwsh` returned `Access is denied` and `powershell` ran cleanly — ruling out a UAC/elevation explanation. This is a deliberate corporate security posture (PS 5.1 has mature AMSI/Script-Block-Logging integration, PS 7 historically weaker on some setups), not a misconfiguration to "fix." Prefer `powershell.exe` for `DefaultShell`/automation on any corporate-hardened Windows box, and don't spend time trying to get `pwsh` un-blocked.
- **2026-08-26 — `HKCU:\Software\Microsoft\Command Processor\AutoRun` is the real per-user `.zshrc`-equivalent for `cmd.exe`, but it's a footgun for SSH automation:** it fires even for non-interactive `cmd /c "<command>"` (only the `/D` flag suppresses it, and OpenSSH-Windows never passes `/D`) — an AutoRun that launches an interactive shell will hang every scripted one-off `ssh host "command"` waiting on stdin, since the intended command never actually runs. Use the server-wide `HKLM:\SOFTWARE\OpenSSH\DefaultShell` registry key instead — it correctly handles both interactive and one-shot exec without this trap.
- **2026-08-27 — "Generic" templates can still hardcode values if nobody checks for an override mechanism:** `assets/msys2/tmux6.cmd`/`ollama6.cmd` were documented as "carrying no DxO-specific values" (true — no raw IP) but still hardcoded the SSH alias (`server`) and a fixed port directly in the command line, with zero env-var/parameter override. A file can pass a narrow "no secrets/no IP" grep check while still failing the actual goal of a template (copy-and-reuse-elsewhere) — the real test is "can I retarget this without editing the file's logic, only its config?" Fixed by reading `SSH_ALIAS`/`LOCAL_PORT` from the environment with a `REPLACE_ME`/default fallback, matching the bash equivalents.
- **2026-08-27 — `assets/` vs `scripts/` split caught 3 separate times in one pass, same root cause each time:** every new template family (`remote-server`, then `msys2`, then the standalone PowerShell profile) was first written entirely into `assets/`, including the executable `.sh`/`.ps1`/proxy scripts —  caught this 3 times in a row before it was internalized as a standing rule. Anti-repeat: **before writing ANY new file into a skill's `assets/`, ask "is this executable code (`.sh`, `.ps1`, a script with a shebang) or passive config/data (`.conf`, `.service`, `.cmd`/`.bat` launcher, JSON/YAML)?"** — executable code belongs in `scripts/`, mirroring the root kernel's own `scripts/` vs `assets/` split (see root `AGENTS.md` → Kernel Structure Map). This check should happen at file-creation time, not as a retrofit — 3 separate move-and-fix-cross-references passes were needed here because the check wasn't applied consistently from the first file.
