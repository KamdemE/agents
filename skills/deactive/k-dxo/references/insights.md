# k-dxo — Insights

Durable, evolutionary lessons for this skill domain. Read before non-trivial work; append at task end.

- **2026-08-25 — This skill is the ONE removable boundary for DxO-internal knowledge — guard that property actively, don't just declare it:** when migrating Windows-side content into the kernel, the temptation is to put "whatever's related to the Windows machine" in one place for convenience. Resist it: the `.cmd` launchers (`tmux6.cmd`/`ollama6.cmd`) that reach deep-pc6 carry zero DxO-specific values themselves (they resolve everything through an SSH alias) and went to `k-windows` as generic mechanism; only the two files that actually contain a DxO-internal value (the SSH `Host` block with the real internal IP + domain-qualified username, and the public key tied to deep-pc6) stayed here. Anti-repeat: before adding any file to this skill vs. a generic one, ask "does this file's own content, if read in isolation, reveal something DxO-internal (an IP, a domain user, a portal URL, an account)?" — if no, it belongs in the generic skill even if its *use case* is DxO-related.
- **2026-08-25 — A migrated Windows-side skill was missing `allowed-tools` and `Insights Discipline`/`references/insights.md` that sibling skills (`k-deep-pc6`, `k-blglaptop139`) already had** — a structural drift that had gone unnoticed. Anti-repeat: when touching any skill for a substantive reason, do a quick structural-contract check (frontmatter fields, Insights Discipline block, changelog row limit) against a sibling skill of the same kind, not just the specific content change requested.
