## Current Seed Insights

- **[2026-09-02] Native interface parity beats parallel abstractions:** when extending an existing runtime mechanism, do not invent defaults, catalogs, or selection paths that diverge from its native control model. `opencode-help` must require the same explicit OpenCode-delegable subagent selection that the caller already receives; model policy stays operator-owned in JSONC. Validate the live native capability before allocating durable state.

- **[2026-08-25 bis] Agent-scoped gates must tolerate in-session agent switches, and must NEVER drain-before-validate:** on blglaptop139 the tmux-notify chain stayed silent even after the plugin loaded: server logs (`stream ... agent=build`) revealed KπX had switched agent mid-session — `currentAgent()` resolves the LAST message's agent, so the session presented as `build` while `TARGET_AGENTS=["Colab","Agent"]`. Worse, `flushToSession` drained its queue (`takePending`) BEFORE the gate check, so every gated-out notification was permanently destroyed with zero trace (no error log — the early `return` is not an exception). Anti-repeat: (1) any TARGET_AGENTS-style gate must include ALL agents that can legitimately own a build-mode session on ANY machine (`Colab`/`Build`/named agents), since operators switch agents freely; (2) validation gates must run BEFORE consuming queued state — drain-after-validate, never drain-before-validate; (3) "silent data loss" bugs hide behind early returns, not exceptions: when tracing delivery pipelines, log every gate rejection explicitly.

- **[2026-08-25] Flatten/move passes must re-test the moved file's OWN imports — `node --check` does not resolve them:** `tmux-notify.js` was silently dead on every machine for 9 days after being flattened `plugins/tmux/` → `plugins/` (2026-08-16): all EXTERNAL references were updated, but the file's own `../libs/agent-scope.js` import became one-level-too-high (→ nonexistent `scripts/libs/`). ESM static-import failure = plugin fails to load entirely, zero hooks registered, and opencode logs nothing loud — symptoms are only "the feature quietly never fires" (no `<tmux-armed>`, no `<tmux-notify>`). Anti-repeat: (1) after ANY file move/flatten in `.agents/`, run a live import test on the moved file itself (`bun -e "import('<abs path>').then(...).catch(...)"`) — syntax checks are NOT enough; (2) when a plugin feature "never fires", first check whether its `<tmux-armed>`-style synchronous side-effect appeared at all: absent side-effect = plugin not loaded (import/config problem), present-but-silent = logic/gating problem; (3) loop a bun import test over EVERY path registered in opencode.jsonc `"plugin"` to get full blast radius in one command.

- **[executor] [2026-07-21] Windows Terminal + tmux OSC leak:** `c/0000rgb:xxxx/xxxx/xxxx` artifacts. Root cause: Win32-OpenSSH fragments OSC responses across TCP packets. Fix: upgrade Win32-OpenSSH to v10.0p2+ on Windows. Do NOT set `SSH_TERM_CONHOST_PARSER=0` (causes tmux visual glitches). Do NOT disable `smcup@:rmcup@` in tmux (breaks pane borders/rendering). Minimal tmux `escape-time 100` is safe insurance.

- **Network triage pattern:** If `ping` and raw TCP connect succeed but SSH hangs during banner exchange on both the main host and inner routed hosts, while another control-plane port (for example Proxmox `8006`) still answers, suspect a host-side firewall/conntrack/sshd pathology or selective payload drop rather than total node loss. Distinguish "host alive" from "interactive control plane unavailable" early.
- **Noisy-PC triage:** For fan/noise complaints, collect live `ps` + `sensors` data before speculating. A single Chromium-family renderer plus its GPU process, combined with an editor like Zed/VS Code, can push package temps into the 90°C range even when system load average looks only moderate; check per-process CPU and thermal readings together.
- **Post-boot terminal latency (ISS-20260706-001):** If Ctrl+T takes 20-30s after reboot but works instantly after ~1min, the root cause is `xdg-desktop-portal-gtk.service` racing with the Wayland display. It crashes with `cannot open display:` → systemd retry cascade → session bus saturated → D-Bus activation of `gnome-terminal-server` blocked. Fix: (1) systemd drop-in `ExecStartPre` that waits for `org.gnome.Shell` D-Bus before portal-gtk starts; (2) pre-terminal service that starts `gnome-terminal-server` after display is ready. Mitigation: the shell startup (oh-my-zsh at ~1.5s) is unrelated to this bottleneck.

- **OpenCode Extension Hooks (State Leakage & New Session Payload):** When writing hooks for OpenCode (e.g., `messages.transform`), **never use global module-level variables** (`let _agent = null;`). Extension modules are cached, meaning global variables leak across all parallel requests, sessions, and agents, causing severe cross-agent pollution. Furthermore, on the very first turn of a *new* session, OpenCode user messages do **not** contain `msg.info.agent`. Hooks relying solely on `msg.info.agent` will silently fail on new sessions. Fix: Always use a dynamic, stateless fallback that checks the incoming `_input` payload (`_input.agent` or JSON string inclusion of `"agent":"Target"`/`"You are Target"`) and iterates over an extensible `_TARGET_AGENTS` array.
- **Skill `references/log.md` rotation structure (GRAVÉ, corrected 2026-08-04 after KπX flagged the violation):** A skill's `references/log.md` archive MUST stay as **exactly ONE `##` section**, with every rotated changelog row stacked underneath it **in chronological order** (oldest first), like a real append-only log. **NEVER create a new `## Changelog rotation — <date/topic>` sub-header per rotation event** — this fragments the archive into disconnected mini-sections and breaks the established convention. When a `SKILL.md` live changelog table is compacted, append the rotated rows to the BOTTOM of the file's single existing section (no new heading), in chronological order relative to what's already there. This applies to every skill's `references/log.md`, not just one.
- **tmux pane silently stuck in copy-mode (`pane_in_mode=1`) swallows all `send-keys` input with zero error:** If a pane stops advancing (same prompt/timestamp after repeated `send-keys`, including a plain `echo`/`printf` probe), check `tmux list-panes -F '#{pane_index} in_mode=#{pane_in_mode}'` before assuming the shell is hung or a command is misbehaving. `in_mode=1` means the pane is in copy-mode/a special mode intercepting keys as navigation, not shell input. Fix: `tmux send-keys -t <target> -X cancel` (or a normal `q`/`Escape` while genuinely in copy-mode), THEN re-send the real command. `tmux capture-pane` will keep showing old/stale scrollback content in this state, which can look confusingly like "the command ran but produced old output" — always cross-check `pane_in_mode` first, not just the captured text.

Do not reintroduce the forbidden change indirectly through a different file or mechanism without a new, explicit go-ahead.

- **Proxy daemon ownership must not infer a stale lock only from a temporarily absent socket (2026-08-12):** An O_EXCL lock winner can be alive between creating its lock and binding its Unix socket. If contenders probe only the socket, one may delete that new lock and launch an orphan daemon. Write the owner PID into the opened lock descriptor before close; on EEXIST, first test that PID with signal 0, then use a socket probe only when the PID is dead or malformed. `whats-proxy` proved the root fix with two consecutive eight-spawn stress runs.
